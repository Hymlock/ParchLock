## E1 Hold an item over Yourself does nothing (all modules)

Repro (412x900 touch, Anchorhead, real grip drag onto Yourself, held 1.2s):

- The drag is active, `dwellStart` is set and `interactionReady` is true, but no radial opens.
- `openYourselfRadial` returns early because `yourselfCommands` is empty.
- `yourselfCommands` returns [] when `!ref.verified` (EquipmentUI.js ~45).
- `Actionable.referenceFor().verified = unique && !customUnverified`. Any object with a stored
  non-default `parse_name` (`ZRamReader.objectHasCustomParseName`) is "customUnverified".
- Measured: umbrella verified, so it gets a full radial. Trenchcoat, clothes and wedding ring
  are `unique=true, verified=false`, so they get nothing. Treasures uses custom parsers widely,
  so effectively every item fails.

The plan already rules on this. PRODUCTION_PLAN "2026-10-01 regression correction (supersedes
conflicting gates above)": "A custom parse_name routine alone is not evidence of ambiguity.
`referenceFor.unique` means one current-scope vocabulary candidate and retains normal click/drop
interaction; `referenceFor.verified` additionally excludes unverified custom parsers; new D198
object-specific provenance requires verification or an opcode-state witness."

The Yourself radial is an interaction, so the gate must be `unique`. Learning keeps its own
`verified`/opcode gate inside AttrCalibrator (`recordExactForm` / `_recordD198Provenance`), so
nothing new is learned on unverified references. The fix is to change the gate in
`yourselfCommands`, which `selectYourselfAction` also uses for revalidation.

Separate visual note from the screenshot: the grip handle is drawn mid-row over item names
("burlap⋮armor"). To be checked; it may be the D98 CSS change.

## E2 Import fails until the module is loaded, closed and reloaded

`ParchLock.GameId` is written in only two places:

- ParchLock.js:33 reads `localStorage PL_GameId_<file>`;
- lib/main.js `Dialog` sets `ParchLock.GameId = cur_gameid` when a native file dialog opens.

`CheckNativeDialog` persists it.

On a fresh install, no native dialog has opened, so GameId is "" and `ImportPackageData` throws
"Wait for the story identity before importing saves". After any dialog opens and the app reloads,
the value is persisted, which explains the "close and reload" workaround.

The Z-code GameId is exactly the hex of header bytes 0..29. Treasures header30 =
08000009f018f019cb11010a696bc5ca00503133303631340042fffa49e5, identical to the save key's game
part. Fix: derive the GameId from the loaded executable's header at story load when it is empty
(Z-code). Glulx needs its own check of the Quixe/Glulxe signature before claiming it.

## E4 Transcript shows one screen

`ParchLockQol.GetTranscriptText` clones the current `.BufferWindow` DOM only. Restore and screen
clears drop earlier text, and nothing is persisted.

Proposal: a running per-module transcript store. Append visible narration and echoed commands
per turn, excluding probe-owned/aria-hidden lines (the same exclusions as
ReadAloud.speakableText). Key it by module plus executable digest. Mark save/restore/restart
events in the stream. Bound the size by trimming the oldest. The viewer shows the stored
transcript. Optional: on restore, show up to the matching save marker.

## E5 Two swords as instances of one item; damage gone; in-place changes not refreshed

No save with both swords exists (the newest is 10-06, Gravel Pit), so this is code-level only:

- (a) The "instance 6/7" badges come from the shared-reference gate when `referenceFor` sees
  several candidates for the noun. The descriptors (gladius vs two-handed) should make each
  unique. Suspect `disambiguatedNoun` collapses to "sword" (hyphenated "two-handed", or a
  dictionary truncation of "gladius"). Needs a live state.
- (b) DAMAGE/HIT ODDS come from the PROWESS probe. With two weapons the reply format likely
  changes, so the regex no longer learns them. Needs the actual reply text.
- (c) Equipment re-renders from `Actionable.RenderInventory` (called every Refresh,
  Actionable.js:1410). So the stale list after USE RAG WITH GINA is either a payload inventory
  that has not been re-read from RAM, or a name/observed-label gate hiding the new object until
  its name appears in INVENTORY text. Needs a live state.

## E3 addendum (operator suggestion, received after sealing; noted before reading Codex)
