Tree Order: Current_Room -> child -> sibling -> sibling ...

Inventory Panel: Traverse child(player_obj) separately. Group items by worn vs. carried.

Dictionary Extraction: For every object in scope, extract its dictionary vocabulary words (name property array) and string pointer (short_name).

5. Deterministic Verb & Action Synthesis (Radial / Context UI)
Derive valid interactions directly from RAM attribute bitfields for all DISCOVERED objects:

Attribute Mapping:

#### 2.3 Hybrid Grid-Force Layout Solver (Mixed Cardinal / Non-Cardinal)

To support games that mix cardinal directions with non-cardinal exits in the same graph:

1. Node Clustering & Constrained Physics:
   - Cardinal Edges: Enforce hard relative offset vectors [dx, dy, dz]. Group adjacent cardinal rooms into "Rigid Structural Clusters".
   - Non-Cardinal Edges: Apply soft distance springs between nodes or clusters.

2. Cluster Collision Resolution:
   - Treat entire Cardinal Clusters as rigid bodies in the force simulation.
   - Calculate cluster bounding boxes and apply inter-cluster repulsion forces to prevent overlapping sub-maps.
   - Anchor non-cardinal edge lines directly to the perimeter of the respective cluster nodes.
The map layout engine actively runs a continuous Graph Beautification Pipeline to ensure the canvas remains clean, readable, and intuitive to navigate at a glance.

Instead of letting nodes scatter into a chaotic spiderweb, the layout engine enforces five core aesthetic and readability rules:

Core Layout Beautification Rules
Edge-Crossing Minimization (Planarization): The solver continuously calculates edge routes to prevent connector lines from crossing over each other or passing straight through room boxes.

Orthogonal Grid Alignment: Cardinal exits (N/S/E/W) snap strictly to $90^\circ$ right angles and clean grid lines. Parallel hallways render as straight rows rather than jagged stair-steps.

Label & Node Collision Prevention: Room title boxes, exit badges, and item indicators dynamically repel neighboring elements, ensuring text never overlaps or becomes obscured.

Looking at the complete pipeline from VM memory inspection to the UI canvas, there are 5 critical missing subsystems that must be built to handle real-world engine behavior and edge cases:

1. Save / Restore / Undo Synchronization Engine
The Problem: If a player types RESTORE, loads a save file, or uses UNDO, the VM's internal RAM rewinds to a previous state, but your UI map graph and discovered object set will stay in the future—causing total state desync.

The Solution: Hook directly into the interpreter’s opcode loop (Z-Machine @restore/@pop/@undo, Glulx restore/restorestat).

Behavior: When a state restoration opcode resolves, the overlay triggers a Full RAM Re-Sync: it purges temporary scope state, re-queries parent(player_obj), and rewinds the map highlight to match the restored turn's Object ID.

2. Compiler Schema Fingerprinter (I6 vs. I7 Memory Layouts)
The Problem: Inform 6 and Inform 7 both compile to Z-Machine and Glulx, but they arrange property tables, dictionary headers, and attribute byte sizes differently (e.g., I6 uses a fixed property table offset; I7 uses dynamic block pointers).

The Solution: On game initialization, run a Memory Schema Fingerprint Check:

Inspect the header flags and search for compiler signature strings in static memory.

Dynamically load the correct offset map (Inform6Schema, Inform7Schema, PunyInformSchema) so property lookups like n_to or short_name never read garbage bytes.

3. Unambiguous Parser Command Synthesizer
The Problem: If a room contains two keys, clicking "Take" on a key in the radial menu and injecting TAKE KEY into the engine will cause the game to pause and ask "Which key do you mean, the brass key or the iron key?".

The Solution: When generating commands from a clicked Object ID (e.g., Object #142), don't just send the short noun. Query Object #142's dictionary array for all attached adjectives.

Result: Synthesizes the most specific unique string available: TAKE SMALL BRASS KEY, completely bypassing parser disambiguation prompts.

4. Pathfinding Macro Queue & Interrupt Handler
The Problem: When a player clicks a distant room on the map and the pathfinder injects a 6-command sequence (n, e, open door, e, climb stairs, n), an event might halt the player mid-route (e.g., an NPC blocks the door, or a light source goes out).

The Solution: Implement a Step-Wise Command Queue:

Instead of blasting all 6 commands into the buffer at once, inject commands one turn at a time.

After each turn, re-evaluate parent(player_obj). If the player did not successfully reach the expected intermediate room node, clear the queue and alert the player with an "Route Interrupted" status.

5. Darkness & Light Scope Suppressor
The Problem: When entering a dark room, the VM still holds all object locations and exit connections in RAM. If the engine blindly reports RAM scope, the map overlay will display items and exits that the player cannot see in pitch darkness.

The Solution: Enforce a Light Check Gate prior to scope evaluation:

Check if Current_Room has the light attribute bit set.

If false, scan player_obj inventory for any item with the light bit set AND (switchable == false OR is_on == true).

If no light source exists: Suppress all room items and exit stubs, lock the UI room node to an "In Darkness" visual state, and restrict radial actions strictly to inventory items.

C++ for the Core Engine (High Performance & Precision):

By writing your memory scanner and force-directed graph solver in C++, you can hook directly into the VM memory structs without serializing memory back to JavaScript on every turn.

You can compile your C++ solver into a high-performance .wasm module.

TypeScript for the Overlay Layer (DOM Native):

Browsers excel at rendering HTML5, CSS, SVG, and Canvas overlays via JS/TS.

TypeScript receives the processed UI payload from your C++ Wasm module and handles input injection, radial menu animations, and DOM rendering.

If you want maximum speed to deployment: Stick to TypeScript. It reads Emscripten linear memory (Module.HEAPU8) easily, has zero build-step friction with Parchment, and manages graph math easily for standard IF maps under 500 rooms.
