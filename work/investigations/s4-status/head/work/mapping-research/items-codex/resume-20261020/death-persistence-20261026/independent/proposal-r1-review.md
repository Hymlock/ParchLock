# R1 adversarial design review — REVISE

Core cumulative-per-run ledger design accepted in principle. No implementation reviewed or executed. Required revisions:

1. Enumerate all explicit new-game owners, not only native RESTART and story-ended UI. Current MapTopology.handlePossibleNewGameAnswer reaches StatTracker.Resync("new-game") at js/MapTopology.js1069 when player declines startup restore; this has no SaveState lifecycle event. Tutorial.close(true) at js/Tutorial.js672-673 performs location.replace(location.href) expressly to start fresh. Under R1 these can adopt the prior active run after a real new start. Specify common idempotent new-run intent/event handling at these owners; add both native browser proofs. Add MapTopology/Tutorial and Tutorial status prose to potential write set. If tutorial completion intentionally keeps run history, amend its promise and explain; do not silently count separate freshly restarted games together.

2. Specify durable new-run/pointer write failure semantics. Ledger and active pointer are multiple localStorage writes. Failure between them can leave reload pointing at the prior run, contaminating new events or resurrecting the old count. Likewise a restored prior run must not increment a cached newer run after pointer-write failure. Use memory-selected run authoritative for the current page, explicit ordered writes/recovery rules, and a persistent intent or equivalent protection for reload failure. R1's generic 'retain unsaved in-memory counts' is insufficient across navigation. Pre-navigation new-game intent must be exact-story scoped, consumed once, and not erased before new ledger/pointer creation succeeds. Report inability to make the new selection durable. Test failure at EACH write position and reopened page state, not only a single setItem exception.

3. Concretize late-digest operations and event attribution. 'same story context verified' needs an exact token/path-generation rule; pending death/restore/new-game/save operations must be ordered and scoped, discarded on context change, and attached to their selected run rather than whichever pointer exists when digest resolves. SaveState.snapshot currently can see no digest and silently return, so a successful early save could otherwise lack linkage after identity readiness. Pending snapshot must retain its selected run plus safe snapshot at save time, not later abandoned map or later run. Restore before StatTracker initialization must bind before load/adopt; late digest must not replay a cleared ending. Add late digest native lifecycle permutations, including save->restart->digest, death->restore->digest, and story switch before promise resolves.

4. Specify bounded seen-episode storage. Persisting all episode keys forever grows the ledger and every ending serialization; count and dedup may fail after quota. R1 says bounded IDs but not bounded key length/count or validation of imported/local episode arrays. Existing key is ending|pageEpoch|episodeId, and replay across new pages is already excluded by ending capture. Define retention sufficient for same-page duplicate calls and preserved local keys on import, with count monotonicity and overflow behavior. Reject/ignore invalid local and package data before arithmetic; increments at MAX_SAFE_INTEGER must not write an unsafe count.

5. Pin missing-sidecar association failure behavior and failed overwrite behavior. Binding an observed unlinked restore to current run is an intentional chosen policy, acceptable given old-save ambiguity, but persist it without falsely copying abandoned map/labels or silently replacing unrelated corrupt metadata with arbitrary active identity. If this binding cannot store, report non-durability and retain current-page selection. A newly successful native SAVE overwrites old save bytes: if snapshot write fails, old association must be removed exactly as current stale-map protection; the ledger may remain. Test separate-runs same filename overwritten under quota, then reopen/restore. Missing metadata cannot identify an historical run; document this limitation explicitly to user when material.

6. Import list must be pure and complete before mutation, deduplicated per storage key and run, and no in-memory SaveState caches may adopt imported totals before successful transaction completion. Current Qol.js597 invokes importWrites only after native save writes, but before mutations a complete list can be calculated without depending on newly written native bytes. Current rollback covers returned keys; use it with each prior value captured once. On rollback keep memory ledger/selection unchanged; after success refresh only the currently selected matching run's displayed totals if needed, without switching active run. Test failure after run write and after last sidecar, repeated save entries, same-run several records, import local higher total, and export quota-failed in-memory latest total behavior. Specify whether export uses in-memory current run when ledger persistence failed; otherwise exported old-save/latest promise is false in this recoverable state.

These are design gaps, not rejection of ledger approach. Coupled wins are explicitly authorized by R1 and must use same validation, binding, isolation, overflow and failure semantics. Keep D178/D180 invalidation and D215 count qualification unchanged. No further concern with exact-digest namespace, same-ID max merge, retaining run on deleting one save, or author-free full gate/APK sequencing once above is resolved.
