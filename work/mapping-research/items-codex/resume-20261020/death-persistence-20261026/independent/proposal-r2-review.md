# R2 adversarial design review — REVISE (two final lifecycle gaps)

R2 resolves the R1 concerns substantially; single-document ledger, bounded recent keys, explicit new-game owners, precomputed rollback and no-RNG identities are acceptable. Two ordering cases still need explicit rules before consensus:

1. Retained new-game intent must track/supersede the latest authoritative run selection, not permanently force its original new run. Repro: prepare restart intent R2 -> new page ledger quota failure leaves intent R2 -> native RESTORE selects saved R1 -> ledger write for R1 succeeds -> F5. R2 currently says retain intent until ledger stores 'that selection', so stale intent R2 could reselect the wrong run on the next boot. On successful later RESTORE/new-run, supersede or clear intent consistently with current selection; clear only after current selection is durable. If current selection cannot persist, update intent to it where possible, reporting if neither store can preserve it. Avoid a duplicate reset if same-page new-run is followed by a restore before navigation. Include this exact quota->restore->reload control and restore->restart->reload counterpart.

2. Deferred restore must capture the restore-time binding, just as deferred save captures its map/labels. R2 queues successful restore(name) and resolves saved metadata 'at that point' during FIFO draining, but it does not say whether sidecar is read at event or drain time. Counterexample digest pending: native RESTORE A points R1; then native SAVE A overwrites it under selected run; later readiness replay reads new A sidecar instead of the metadata associated with the successful restore. Concurrent import/delete can do the same. Capture the raw selected-sidecar/playthrough metadata (or immutable event snapshot) at the actual successful restore when path/storage key identity permits, validate exact digest on readiness, and feed FIFO that captured snapshot. If digest is unavailable so exact sidecar key cannot yet be constructed, explicitly preserve ordering by staging sidecar writes/deletes/imports and materializing each restore against the virtual sidecar state preceding it, rather than reading a changed disk name out of order. Qol import should either require exact digest readiness before any native writes or join this same ordered operation scheme. Test late-digest restoreA->saveA, restoreA->deleteA and attempted import before readiness.

No further design blockers after these explicit amendments. No production edits/tests/builds performed. This is design review only, not implementation acceptance.
