## Current source evidence

1. StatTracker blank() initializes deaths/wins=0 (1532-1533). countEnding (1475-1492) adds an episode fingerprint to seenBanners, increments the count, saves the whole model under PM_Stats_<gameIdentityKey>, and displays the notice. This is currently a module-stat model, not a native-save snapshot.
2. StatTracker.load (1558-1591) overlays stored model fields, then calls forgetReadings(m) with no second argument. forgetReadings (1672-1675) treats that as resetting playthrough and sets deaths/wins=0. observe (1849-1852) calls load when key or story filename changes. Thus persisted serialized counters are deliberately discarded on a fresh page/identity initialization. The quit/reopen loss is directly explained by this source chain.
3. Resync (1687-1710) invokes forgetReadings(model, reason===restart || reason===new-game). Same-page restore_file/undo therefore retain counts; accepted restart/new-game zero them. Existing death-terminal assertions 135-139 explicitly enforce same-page restore=2 preserved and restart=0. They do not test reload/native-save persistence.
4. SaveState.snapshot (96-108) stores schema/story/savedAt/map/labels only. read (71-80), applyPending (113-145), validImport (199-207), and importWrites (213-224) have no death/win state. So neither saves nor exported packages can re-establish counters after StatTracker.load clears them. This also means a per-save numeric snapshot alone would conflict with the old same-playthrough restore rule if restoring a pre-death save lowers the count.
5. Transcript.commitSave (185-192) calls SaveState only after native successful-write ownership; commitRestore (170-182) stages the selected name after successful restore. onVmEvent (154-166) distinguishes boot restart and autorestore. collect (313-322) calls boot only without observed autorestore. These existing authoritative hooks should remain owners rather than introducing attempted-command-based persistence.
6. UndoRestoreSync.resync applies staged SaveState at 38-40 before StatTracker.Resync at 60 and before WorldModel tick. Therefore a future restore payload must survive later stat invalidation and first observe/model initialization; simply assigning deaths in applyPending risks overwrite on late identity initialization or restart reset.
7. SaveState sidecar identity is executable digest plus native save name; StatTracker uses ZRamReader.gameIdentityKey with unknown fallback. A persistence design must not accidentally scope counters to a potentially shared stats key rather than the exact executable and actual playthrough.

## Prior contract and interpretation

D178 is about stale score/weight/carry readings, not a reason to erase product event history on resuming a save. D180-D183 retain learned pins and suppress false score badges/cues across restore. Preserve those protections; do not solve this by generally retaining old readings.

D204/architecture 68 explicitly say module load/New Game/accepted RESTART reset counters and undo/restore retain them within a playthrough. D215 reuses that contract; architecture75 restricts SaveState to map/display labels. The new operator request supersedes the module-load reset where load resumes the saved playthrough. It requires an explicit amendment rather than pretending current behavior is an accidental failure to serialize.

Best reading: deaths are accumulated history for one playthrough, survive quit/reopen and rollback to an older save belonging to that playthrough. Save files provide durable connection to the playthrough, not merely the number at their historical snapshot. Otherwise restoring the save immediately preceding a death erases that death, contradicting both 'persistent for the playthrough' and the old D204 same-page behavior. A stable playthrough identity plus persisted event totals, referenced by save snapshots, would distinguish replay/rollback from genuinely separate New Game runs of the same executable. New Game/restart should establish a distinct playthrough; restoring an old save may re-enter the old playthrough. Do not use max across every save of the executable: separate runs could inherit one another's deaths.

Ambiguity: operator's 'previous set' may mean previous save, not a separate historical playthrough. If they intend historical snapshot count on restore instead, that changes D204 restore semantics. Wins are structurally coupled but the explicit issue is deaths; any expansion to wins must be named and consistently tested. Missing/corrupt sidecars and pre-change saves need a clean defined behavior without migration, per seat rule15; never guess a run from module-wide stale counts.
