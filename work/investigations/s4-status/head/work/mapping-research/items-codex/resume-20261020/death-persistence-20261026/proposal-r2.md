# Death persistence R2 — explicit revision after blind/adversarial review

R1 comparison and all unchanged detection/reading/validation/gate/APK constraints remain. This document supersedes R1's storage and lifecycle implementation details. No production implementation yet.

## 1. Atomic ledger and durability

Use ONE localStorage document per exact executable digest: schema1/story/active/runs. Each run has safe deaths/wins and bounded recent episode IDs. Active pointer and record totals commit in the SAME setItem, so there is no split ledger/pointer write. Current-page selection and unsaved outcomes remain authoritative in memory after a write failure; never revert to an older cached run. Retry persistence at subsequent legitimate lifecycle/readiness boundaries, not a busy timer. Report actual non-durability once per outstanding failure, clear the warning latch after successful persistence.

Explicit pre-navigation new game uses a small sessionStorage intent {schema,path,runId} scoped to normalized exact StoryPath; no game RNG draws. Persist intent before navigation. If that intent cannot store, do not navigate; report. New page consumes its runId exactly once, retaining the intent until the ledger atomically stores that selection. If ledger write fails, memory selects that new run and retained intent prevents old active selection on another same-tab reload. Accepted native restart creates memory selection immediately; attempt to persist intent and ledger. If both stores are unavailable, report non-durability explicitly—no claim of recovery when all storage is unavailable. Old durable run data is not deleted to fake success. A save snapshot can still carry its validated run id/totals if save metadata itself writes successfully.

## 2. All new-run owners / one transition each

A. Transcript's successful native restart event while genuinely in-game owns one new-run operation. Boot restart is excluded. StatTracker.Resync('restart') clears readings but does NOT create a second run; it adopts SaveState totals. Repeated UI/tick resyncs do not create IDs.
B. Startup-restore decline uses the existing D182 StatTracker.Resync('new-game') event from MapTopology exactly once (its awaiting-answer latch already prevents duplicates). Only this reason explicitly starts a run; ordinary unknown resync does not.
C. Tutorial.close(true) on play page and explicit story-ended Restart use prepare-new-game intent before location.replace/reload; library-phase tutorial close does not. Cancel/Skip/no navigation does not reset. Update tutorial/help prose.
D. Reopen/quit/F5 and fresh VM boot without explicit new-game intent retain selected run history; existing fresh-map handling stays unchanged. Successful restore may select another saved run. Accepted engine autorestore retains current run.

Transcript must forward successful save/restore/restart counter lifecycle even when transcript metadata/digest is not initialized; it may skip transcript operations themselves. Its restart boot guard may use actual accepted page submissions to distinguish a later real restart while identity is late, never attempted RESTART text alone. No change to outcome qualification. Boot/late-hook/native and cancelled-restart controls required.

## 3. Concrete late identity/context order

Context is normalized ParchLock.StoryPath (fallback normalized URL story), plus a monotonically changing page-context generation token. Use ModuleLibrary.currentExecutableDigest(path) with the explicit path, NOT an unqualified potentially stale global digest. Any path change drops pending operations/cache for the abandoned context. Digest readiness callback captures path+generation and ignores mismatches. No shared unknown namespace.

Until the exact digest is ready, keep FIFO operations (maximum256 with explicit failure report if exceeded): ending(key,outcome), successful save(name, immutable map/label snapshot captured AT save), successful restore(name), new-run(allocated opaque id), forget(names). Run selection is symbolic in sequence: initial resume handle resolves from that story's active ledger; restore resolves its saved run at that point; new-run uses its allocated id. Thus save->restart->digest binds save to earlier run; death->restore->digest attributes death to earlier run and selects restored one; a story switch cannot drain old operations into the next story. Store neither later map nor later selection in an earlier save. When digest becomes ready, materialize operations in order, applying same-ID counts and event dedup, then persist ledger and pending sidecar writes. Run IDs are allocated once per operation and reused on retry, never regenerated by poll/tick.

Native Map/label behavior remains under existing SaveState staging. Counter selection is independent of map presence/validation; a malformed map does not itself grant or erase counter identity. Capture/read playthrough metadata independently with strict schema/story/run/counter checks. StatTracker load/Resync invalidates readings as before, then adopts materialized selected totals; no imported/old PM_Stats counter is used as run authority. Early endings may display their current-page increment while prior total is unknown; after identity it reconciles with the correct selected history. Queue is not replayed as fresh ending detection.

## 4. Bounded dedup/arithmetic

Run IDs strict p_-prefixed ASCII length<=96, generated with crypto UUID/random bytes; fallback time+monotonic nonce with collision check, never Math.random/game RNG. Episode IDs strings<=256, retain the last128 distinct IDs per run. Existing current-page model.seenBanners and ending latch also protect same-page duplicate callbacks; a new page's epoch differs and startup/replayed output is excluded. Validate local record shape and bounded counts before arithmetic. Nonnegative safe integers only; saturate at MAX_SAFE_INTEGER with an actual overflow/non-durability notice rather than writing unsafe values. Package snapshots contain id/deaths/wins only, not untrusted replay fingerprints. Merge keeps local recent IDs.

Limit document runs to2048 and pending operations to256; refuse/report capacity exhaustion instead of deleting linked history or inventing totals. Malformed local documents are not overwritten silently: persistence remains blocked/reported until a valid selected save can be handled explicitly; never copy learned module-wide totals. Fixtures include invalid shapes/IDs/keys,129 recent IDs, unsafe and overflow counters.

## 5. Missing bindings, overwrites, failures

A named successful restore with no playthrough metadata continues the selected current run, preserving old same-page behavior; attach that observed association to that name. This deliberately does not reconstruct a historical run. Keep valid existing map/labels; if absent use clean empty map/null labels, never abandoned current data. Missing filename cannot create a named association. Malformed playthrough metadata is unknown, not a valid foreign run; do not overwrite unrelated corrupt payload as if it was trusted. Report actual metadata corruption/binding failure. Missing metadata can only retain/recover counts recorded by the new system; do not invent previously lost history.

A newly successful native SAVE captures the new run and snapshot. If sidecar write fails after native bytes overwrite the name, REMOVE the old sidecar (existing stale-map protection), retain selected ledger/memory, report actual metadata failure. Never leave old-run binding beside new save bytes. Failure in ledger write versus sidecar write is tracked separately. Snapshot contains current run/id/totals, allowing recovery if ledger alone is missing. Delete one save removes only that sidecar; uninstall removes exact-story ledger/intent/sidecars; prior runs are otherwise preserved.

## 6. Portable transaction/cache

SaveState.exportFor uses max of SAME-ID valid persisted and current in-memory counts, including newer undurable outcomes, for selected saves only. It cannot fabricate metadata for an old unrelated save; snapshot failure is reported, not silently disguised. Pure importWrites computes one deduplicated ledger write plus one per selected sidecar and no active selection change from imported IDs. It may include genuine current pending native history in the SAME-ID merge; it does not adopt imported totals into memory. Validate all entries first. Several saves sharing an ID merge once; local higher totals/recent keys survive. Duplicate native storage keys reject before mutation.

Qol computes the complete SaveState write plan BEFORE the first native/map write, captures each original storage key once and rolls back every applied run/sidecar/native key on failure. No SaveState cache adoption or StatTracker sync until successful transaction completion; after success refresh only the currently selected run, never switch to an imported run merely because it was imported. If rollback runs, caches/selection retain pre-import native state; later reads reflect restored disk plus legitimate unsaved native history. Test failures after ledger and each sidecar, repeated entries, rollback and export after ledger quota failure.
